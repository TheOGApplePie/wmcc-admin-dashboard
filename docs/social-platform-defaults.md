# Campaign platform defaults and content approval

Campaign creation and settings support independent Instagram, WhatsApp and TikTok defaults. Each default contains a message and an optional poster with alt text. Initial values come from the linked event's description and poster. Editing one platform does not change another. Custom values remain when the linked event changes. Reels still require an appropriate video before approval; storing a poster default does not bypass format validation.

Apply `044_social_platform_defaults.sql` after migrations 039–043 and before deploying these changes. It adds one checked JSONB column to campaigns, extends the canonical generation and copy functions, and retains the canonical save function with additional unresolved-retry checks. No new tables or dependencies are introduced. Existing campaigns receive `{}` and retain occurrence-based fallback content until defaults are configured. The migration does not rewrite existing post content or approval.

Generation selects platform content for every existing proposal type. Preview transformation runs on the backend; the transactional persistence function independently reads the locked campaign's saved defaults. Campaign/event versions, schedule rules, existing conflict keys, and `ON CONFLICT DO NOTHING` stay authoritative. Generated posts retain `proposed` status with no approval.

Use **Copy to posts…** in campaign settings or **Copy post details** in the post editor. The existing modal supports status filtering, explicit checkboxes and per-page selection, with platform/date/status labels and a selection summary. Default copying offers Poster, Message, or both. Post copying also retains the existing optional hashtag field. Filtering never selects posts; changing pages clears the selection. Copying uses the current form values, so saving defaults and copying to posts remain explicit, separate operations.

Copying atomically saves selected posts as drafts and clears publication consent, publisher identity, scheduled execution time and pending attempt time. The proposed date/slot and unselected content remain. Editing a single post offers **Save as Draft** or **Save & Approve**. Approval uses the canonical save function and requires `social.edit` plus `social.publish`. Existing bulk approval remains transactional. WhatsApp approval still records the approver as publisher and requires that user's own paired account. Assignment does not confer approval or sender ownership.

Drafts, proposals, future approved posts, and terminal failed posts without pending retries or provider reconciliation can receive copied content. Approved targets retain the existing additional Publish permission requirement. Due, processing, provider-processing, sent, skipped and cancelled posts cannot receive content. Failed posts with `retryable`, `next_attempt_at`, an external provider ID or `provider_processing_started_at` remain locked. Single saves enforce the same unresolved-provider checks. Existing workers, retry limits, idempotency keys and provider APIs are unchanged.

SQL handles bounded target filtering/pagination and atomic version-checked mutations. The existing copy function retains its bounded per-target locks/validation/audit loop (maximum 500) to preserve transactional behavior rather than adding a competing mutation path. Campaign/post indexes already cover campaign lookups and reserved slots; no additional index is warranted for the new small JSON value. The server handles event initialization, content/media validation, authorization and minimal selection refresh. React holds form values, checkbox selection and feedback. Campaign settings now submit their version so concurrent edits fail instead of silently replacing another administrator's defaults.
